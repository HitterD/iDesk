3 Pendekatan: Notification System Redesign

Pilih pendekatan yang paling cocok — gue akan rekomendasikan satu

A

Enhance Existing Bell

Upgrade NotificationPopover yang ada → jadi Command Center. Tambah urgency tiers, persistent badge, re-surface toast. Tidak ada endpoint baru — pakai data notif yang sudah ada.

Pros

  • Minimal perubahan backend
  • Lebih cepat dikerjakan
  • Tidak break existing flow

Cons

  • Notif bisa terlewat saat kirim (race condition)
  • Action items bergantung pada notif — kalau notif tidak terkirim, inbox kosong
  • Tidak reflect state aktual (ticket mungkin sudah selesai tapi notif masih ada)
B

Action Items API Baru (Entity-State Based)

Endpoint /api/action-items yang menghitung langsung dari state entity — ticket assigned+unresponded, approval pending, renewal D-7, dll. Bukan dari tabel notifikasi. Command Center baru di topbar ambil dari sini.

Pros

  • Selalu akurat — reflect state real DB
  • Tidak terpengaruh notif gagal kirim
  • Auto-resolve saat item selesai dikerjakan
  • Basis solid untuk reminder system

Cons

  • Perlu endpoint baru per module
  • Lebih banyak pekerjaan backend
  • Query perlu dioptimalkan agar tidak lambat
C ⭐

Hybrid: Command Center + Entity-State RECOMMENDED

Command Center baru di topbar yang menggabungkan 2 sumber: (1) Unread urgent notifications yang sudah ada + (2) Endpoint action-items ringan per kategori. Bell tetap ada untuk history. Reminder intensity di settings.

Arsitektur
TopbarCommandCenter
 ├ useActionItems() → /api/action-items (polling 60s + socket invalidate)
 ├ Urgency tiers: 🔴 Critical / 🟡 High / 🔵 Normal
 ├ Re-surface toast (configurable: off/15m/30m/1h)
 └ NotificationPopover (existing, tetap ada untuk history)

Pros

  • Akurat (entity-state) + tidak kehilangan context (notif history)
  • Dapat dikerjakan inkremental per modul
  • Toast persisten yang bisa dikonfigurasi user
  • Tidak ada breaking change

Cons

  • Lebih kompleks dari A
  • Butuh beberapa endpoint baru
